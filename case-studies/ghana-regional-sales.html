Two files. One truth.

Two regional sales extracts, same columns, same shape. Stacking them took one click and produced a total that was wrong by a third. The work was not the append — it was proving which of the two files to believe.

THE SHAPE OF THE PROBLEM

What the two files
actually were.

Two extracts of the same regional sales report arrived days apart. Identical headers, identical grain, no obvious duplicates when you scroll. Four regions appeared in both files — with different values, because the second file restated them after a correction upstream. Nothing in either file said so.

Appended, those four regions were counted twice: once at the old value and once at the corrected one. The result looked plausible, sat in the right order of magnitude, and was wrong by GHS 725,600.

WHY IT SLIPS THROUGH

An append is a decision,
not a step.

Power Query makes combining files feel like housekeeping. It isn't — it is a claim that the two sources are disjoint. Three things hid the overlap here.

No duplicate rows

The overlapping records were not identical, so Remove Duplicates found nothing and every row-level check passed. Duplication has to be tested on the business key — region and period — not on the whole row.

No file said it was a restatement

Neither extract carried a version, a run date, or an as_of column. Which file supersedes the other was a question for the people who produced them, not something to infer from the data.

The wrong total is believable

A 33% overstatement does not look like an error. It looks like a good quarter — which is exactly why nobody questions it until a decision has already been made on it.

HOW IT WAS RECONCILED

Four checks, in this order.

01

Count rows against distinct keys

Group each file by region + period and compare the row count to the distinct key count — in each file separately, then in the appended query. The append was the only one where the two numbers diverged, which located the problem before any measure was written.

Row count = distinct key count is the cheapest data-quality test there is
02

Name the overlap explicitly

An inner merge of the two files on the business key returns exactly the rows that exist in both — four regions here. Anti-joins in each direction return what is unique to each file. Together they answer "how much do these files really share?" in one screen.

03

Decide which version wins — with the source, not alone

The overlapping values differed, so one of them was stale. That is a question for whoever produced the files. Confirmed as a restatement, the rule became the newer file wins — recorded in the query so the next person inherits the decision instead of re-guessing it.

04

Replace, then re-total

Keep the rows in the older file whose key is not in the newer one, append the newer file whole, and re-run check 01. The validated total came in GHS 725,600 lower than the naive append — a 33% difference between a defensible number and a confident one.

HOW IT IS BUILT

The query chain.

All of it happens in Power Query, so the two source files stay untouched and the whole reconciliation re-runs on refresh. Nothing is fixed by hand in a cell.

BEING STRAIGHT ABOUT IT

Scope and honesty.

What this is, and what it isn't

This is a reconciliation of a private regional sales extract. The source files are not in this repository and will not be published, so the only figures shown here are the two that describe the error itself: GHS 725,600 and 33%. Region-level values stay with the owner of the data.

There is no dashboard-of-the-year screenshot attached to it, because the value was not in the visuals. It was in refusing to append two files that looked appendable, and being able to show — on refresh, repeatably — why the smaller number is the right one.

Known limits — the restatement rule ("newer file wins") was confirmed with the data owner and is not inferred from the files; had the answer been "both are partial", the correct fix would have been a merge on the key rather than a replacement.

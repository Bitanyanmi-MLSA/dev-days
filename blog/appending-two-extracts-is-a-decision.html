Appending two files is a decision.

Two extracts with the same columns are not automatically two halves of one table. Stacking them is a claim that they share no rows — and when that claim is wrong, nothing warns you. It cost me a total that was 33% too high, and it took one query to catch.

WHAT HAPPENED

Same columns, same shape, different truth.

Two regional sales extracts, days apart, identical headers. Four regions appeared in both files with different values, because the second file restated them after a correction upstream. Nothing in either file said so — no version column, no run date, no note.

Appended, those four regions were counted twice: once at the old value, once at the corrected one. The result was in the right order of magnitude and looked like a good quarter. It was GHS 725,600 too high — 33%. The full write-up is in the Ghana Regional Sales case study; this note is the reusable part.

Append means "these two sets are disjoint". If you have not tested that, you have assumed it.
CHECK ONE

Row count against distinct keys.

This is the cheapest data-quality test there is, and it catches duplication that Remove Duplicates never will — because restated rows are not identical rows. Define the business key, then compare. 

// QA_KeyCheck — run it on each source AND on the combined table
let
    KeyCols      = { "Region", "Period" },
    RowCount     = Table.RowCount( Sales ),
    DistinctKeys = Table.RowCount( Table.Distinct( Table.SelectColumns( Sales, KeyCols ) ) ),
    Result       = [
                       rows          = RowCount,
                       distinct_keys = DistinctKeys,
                       duplicates    = RowCount - DistinctKeys
                   ]
in
    Result

Each file passed on its own. The append did not. That single number located the problem before a measure had been written — which is the point: find it in the query, not in the meeting.

CHECK TWO

Name the overlap out loud.

Knowing that duplicates exist is not the same as knowing what they are. An inner merge on the key returns exactly the rows that live in both files; anti-joins in each direction return what is unique to each. Keep the overlap query in the file as a visible audit step rather than deleting it once you have looked. 

// The rows both files claim — four regions, at two different values
Overlap =
    Table.NestedJoin(
        Sales_V1, { "Region", "Period" },
        Sales_V2, { "Region", "Period" },
        "v2", JoinKind.Inner
    )

Now the question is answerable by a human: are these restatements (one version supersedes the other) or partial loads (both are incomplete and should be summed)? The data cannot tell you. The person who produced the files can, and that conversation is the actual work.

THE FIX

Replace the restated rows, don't stack them.

Once "the newer file wins" is confirmed, the rule is simple: keep the rows in the older file whose key is not in the newer file, then append the newer file whole. A left anti-join does exactly that, and wrapping it in a function means the next file pair takes thirty seconds. 

// fn-replace-restated-rows
// Rows in `newer` win. Rows in `older` survive only if their key is not in `newer`.
( older as table, newer as table, keys as list ) as table =>
let
    NotRestated = Table.NestedJoin( older, keys, newer, keys, "restated", JoinKind.LeftAnti ),
    Cleaned     = Table.RemoveColumns( NotRestated, { "restated" } ),
    Combined    = Table.Combine( { Cleaned, newer } )
in
    Combined

Calling it

Sales = fn_replace_restated_rows( Sales_V1, Sales_V2, { "Region", "Period" } )

Then run the key check again. Zero duplicates, and a total you can defend line by line.

Two things to watch

  • Column names must match exactly. Table.Combine unions the column sets, so one renamed column gives you a half-null extra column instead of an error. Normalise names before combining.
  • Anti-join direction matters. JoinKind.LeftAnti keeps rows from the first table that have no match in the second. Swap the arguments and you have quietly decided the opposite version wins.
THE HABIT

Three questions before you click Append.

  1. What is the business key — the columns that make a row unique in business terms, not in file terms?
  2. Do the sources overlap on it, and by how much?
  3. If they overlap, which version wins — and who told you that?

Answer them in the query, in writing, where the next person inherits the decision instead of re-guessing it. A model that records why a row was dropped is worth more than one that silently produced the right answer once.

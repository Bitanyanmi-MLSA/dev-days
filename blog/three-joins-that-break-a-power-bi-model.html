Three joins that quietly break a model.

None of these throws an error. Each one produces a number that is wrong by enough to matter and right-looking enough to present. All three came out of the same 100,000-row dataset, and all three are one line to fix once you know to look.

THE PATTERN

Broken models don't fail loudly.

A model that is genuinely broken usually tells you: a blank visual, a circular dependency, a relationship Power BI refuses to create. The dangerous ones are quieter. The report loads, the totals are the right order of magnitude, and the story it tells is confident and wrong.

These three are the ones I check first in any new model, in this order. The examples come from the Olist marketplace model, but nothing about them is specific to that dataset.

JOIN ONE

The key that isn't the thing you're counting.

Every customer table has an ID. That does not mean it identifies a customer. In the Olist data, customer_id is unique per order — a new one is issued every time somebody buys. There is a second column, customer_unique_id, which identifies the person.

Count the first one and your report says every customer is new, repeat purchase is zero, and retention is not worth measuring. It is a coherent, self-consistent, completely fictional story. Counting the second one, only 3.12% of customers in that dataset ever come back — a finding worth an entire meeting.

The fix

-- Count the person, not the transaction record
Unique Customers = DISTINCTCOUNT ( customers[customer_unique_id] )

-- And once the grain is right, this becomes possible
Repeat Customers =
VAR OrdersPerCustomer =
    ADDCOLUMNS (
        VALUES ( customers[customer_unique_id] ),
        "@Orders", CALCULATE ( DISTINCTCOUNT ( orders[order_id] ) )
    )
RETURN
    COUNTROWS ( FILTER ( OrdersPerCustomer, [@Orders] > 1 ) )
Ask of every ID column: is this unique per event, or per entity? The column name will not tell you.
JOIN TWO

The lookup table that isn't a lookup table.

A dimension has to have one row per key. Geography tables almost never arrive that way. The Olist geolocation file holds 1,000,163 rows for a few thousand zip prefixes — one per recorded coordinate. Relate it as-is and Power BI cannot make a one-to-many relationship, so you end up with a many-to-many, and every measure filtered through it is silently multiplied by however many rows that key happens to have.

The tell is that your revenue goes up when you add a geography slicer. Totals that change when you add a filter are the loudest quiet symptom in the business.

The fix

// One row per key, before it is allowed to be a dimension
let
    Source   = Csv.Document(
                   File.Contents( "C:\data\geolocation.csv" ),
                   [ Delimiter = ",", Encoding = 65001, QuoteStyle = QuoteStyle.Csv ]
               ),
    Headers  = Table.PromoteHeaders( Source, [ PromoteAllScalars = true ] ),
    Typed    = Table.TransformColumnTypes( Headers, {
                   { "geolocation_zip_code_prefix", Int64.Type },
                   { "geolocation_city",  type text },
                   { "geolocation_state", type text }
               } ),
    OnePerZip = Table.Distinct( Typed, { "geolocation_zip_code_prefix" } )
in
    OnePerZip

Table.Distinct with a column list keeps the first row per key. If which row you keep actually matters — a city name, a region owner, a price — group by the key and pick deliberately instead of accepting whatever arrived first.

JOIN THREE

Keys that look identical and are not.

The relationship exists, the arrow is drawn, and half your fact rows land in a blank row you never see unless you go looking. Text keys fail to match for three boring reasons:

  • Encoding. The Olist review and category files are Portuguese. Loaded under the default encoding, the accented characters mojibake — ção becomes something that will never equal ção again. Every query loads with Encoding = 65001 (UTF-8).
  • Whitespace. A trailing space is invisible in the preview pane and fatal in a join. Text.Trim and Text.Clean on every text key, always.
  • Case and type. Power Query is case sensitive where the data model is not, and a number stored as text will not match the same number stored as a number. Normalise the key on both sides of the join, in the query, before the relationship is created.

The fix

// Normalise a text key on both sides of every join
Table.TransformColumns( PreviousStep, {
    { "region_key", each Text.Upper( Text.Trim( Text.Clean( _ ) ) ), type text }
} )

Then confirm it worked instead of assuming: in the model view, the row count of the fact table filtered by the dimension should equal its unfiltered row count. If it doesn't, some rows are landing nowhere.

THE HABIT

Ten minutes, before the first chart.

This is the whole check, and it costs less than the meeting where somebody asks why the number moved:

  • For every ID column you count: per event or per entity?
  • For every dimension: row count equals distinct key count?
  • For every relationship: does any fact row land in the blank?
  • For every total: does it change when you add a filter that shouldn't change it?
